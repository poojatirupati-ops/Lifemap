# Settings: standards, market rates, partner overrides
status: done
deps: T2
files: src/engine/settings.ts, src/engine/settings.test.ts

## Goal
One register for every standard (sec 14 type 2/3, 18, 19.6, 27.5): value, plain guidance wording, source with month, label 'Set by LifeMap' or 'Suggested by [partner]', owner (law = fixed and not editable). Same-for-everyone standards apply from the start (listed, labelled, customer may change: 'Your choice', 'Back to LifeMap's figure'). Market rates (mortgage, loan, card APR, deposit, fund charges) are chips never pre-filled; no suggestion where no published source exists (e.g. buying fees). Partner override replaces figures and label. Retirement age and plan-until have NO standard. Data precedence helper: document > typed > plan > example.

## Done when
Test: law values reject edits; partner override changes the suggestion and label; retirement age/plan-until never resolve to a default; precedence order. npm run build and npm run lint pass.

## Review (round 1, score 3)
Build, lint and the 7 tests pass. Defects to fix:
1. Inflation must not be a standard. `STANDARDS.infl` makes `resolve('infl')` return 0.02 "Set by LifeMap" from the start. Spec 14, 22 and 27.4 make inflation a required choice that blocks results and is never defaulted (T13 gate and the "Inflation -> Choose" row depend on it; the prototype only offers its 2% as a "Use the standard" chip, `S.infl` is the customer's own). Move it out of the auto-applied set: keep the figure and wording as a suggestion chip (e.g. in a separate suggested-only block or `MARKET`-style), `resolve('infl')` must be undefined until chosen, and add a test beside retirementAge/plan-until. Same check for anything else 27.4 lists.
2. Derived `inv` ignores the partner block. Prototype `invNet` reads the partner's `invGross` and `fundChg`, so changing the block changes the standard (spec 18: "changes the suggestion everywhere"). Here `resolve('inv', {}, {values:{fundChg:0.02, invGross:0.07}})` still returns the LifeMap figure labelled "Set by LifeMap" (checked by running it). Compute `inv` (and its `vc` and `by` wording, currently hard-coded "5% ... 1%") from the resolved gross and charges, label it "Suggested by [partner]" when either is overridden, and test it. The current "derived investment standard matches the register" test compares invNet to itself and cannot fail.
3. Keys come from customer data but are checked with `in` and `custom[key]`, which walk the prototype chain: `resolve('toString')` returns a function with label "Your choice" (checked). Use `Object.hasOwn` for `custom`, `STANDARDS`, `MARKET` and partner values.
4. `choose` accepts any key and any value: `choose({}, 'zzz', NaN)` and `choose({}, 'wage', 'abc')` both succeed. This is persisted plan data (plansync) so validate at this boundary: key must be a STANDARDS or MARKET key or one of NO_STANDARD, value must be finite and match the entry's unit (number for pct/eur/num/yrs, 3 numbers for pct3, string for choice). Test the rejections.
5. Law label should read "Set by Government · 2026" (spec 14 and prototype T_GOV); `T_LAW` omits the year.
6. Guidance has no source: `GUIDANCE.planEnd` hard-codes 83/86 with no source or date. Prototype keeps life expectancy as register entries with source (CSO Irish Life Tables) and as-at; the card asks for source with month. Give retireAge/planEnd guidance a src and asat. Also the prototype's fundChg note ("Usually between 0.5% and 2% a year (CCPC)") was dropped; keep it (it is sourced, spec 17 allows it) or say why not.
7. Minor: `lawValue` uses `reduce<any>`; type it. Partner override of a market key with no published base (cardRate, buyFees) is untested.

## Review (round 2, score 3)
Build, lint and the 12 tests pass (verified). Round 1 points 1 to 7 are fixed (inflation is suggestion-only, inv follows the partner block, Object.hasOwn, choose rejects unknown keys and wrong shapes, law label, fundChg note, lawValue typed). Remaining defects:
1. No range limits at the trust boundaries. The prototype refuses out-of-range figures (SETBOUNDS, ~line 7118, "M6": lump sum never above the 25% legal limit, growth ceilings so a provider cannot make a plan look better than it is). Here, run: `choose({}, 'lumpSum', 0.9)`, `choose({}, 'wage', 5000)`, `choose({}, 'infl', -3)` and `choose({}, 'retireAge', -5)` all succeed and are persisted; `resolve('lumpSum', {}, {name:'X', values:{lumpSum:0.9}})` returns 0.9 "Suggested by X"; a partner `infl: 0.5` is offered as a chip. Port SETBOUNDS as data (min/max per key, same units) and enforce it in `choose` and in partner values (`resolve`, `suggestion` ignore or reject out-of-range partner figures). Test the rejections. Retirement/plan-until need at least a sane integer age range (prototype ASM: planEnd 50 to 100).
2. Partner values are not type-checked: `resolve('inv', {}, {name:'X', values:{inv:'abc'}})` returns 'abc' labelled "Suggested by X". The same bounds check (finite number of the entry's unit) fixes this.
3. GUIDANCE asat is invented. The prototype's life-expectancy entries cite "CSO, Irish Life Tables No. 17, 2015-2017" with as-at "2015-2017 (latest edition)", so `planEnd.asat` should say that, not 'Jun 2026'. The test regex `/^[A-Z][a-z]{2} 20\d\d$/` enforces the made-up month; relax it to "has a source and an as-at". `retireAge.asat` 'Jun 2026' is also unsourced (Revenue/DSP: use '2026' like the rest of the register unless a month is documented).
4. Minor: derived `inv` built from the customer's own `invGross` or `fundChg` still reads "Set by LifeMap" (run `resolve('inv', {invGross: 0.07})`: value 0.04, label "Set by LifeMap", wording says 7%). Label it 'Your choice' when either is customer-set.
5. Minor: `pv('inv') ?? undefined` is a no-op; drop `?? undefined`.
