# Navigation: back button and screen transitions
status: superseded
deps: D2
files: src/components/nav/*, src/routes/* (router/guard files from T27), src/screens/*.tsx (back wiring only)

## Goal
A consistent back path everywhere: a BackButton header component (visible on every non-root screen, 44px target, labelled), browser and Android hardware back working through the hash router history (no trapping, no loops, guard redirects replace rather than push), step-back inside Discover and other flows, returnTo kept. Animated screen transitions: native View Transitions API where supported with a CSS enter animation fallback, direction aware (forward slides in, back slides out), respecting reduced motion. Focus moves to the new screen heading on navigation.

## Done when
tests for history behaviour (push, back, guard redirect replace); in a real browser at 375px: Welcome > Why here > Discover Q1 > Q2, Back returns step by step and the browser Back does the same; no console errors.

## Review (round 1, score 3)

In a real browser at 375 (own tab): Welcome > Why > Discover Q1 > Q2 with the Back button and with history.back()/forward() returns step by step, h1 focused each time, no console errors; cold deep link /discover?q=3 steps q3>q2>q1>discover>why>welcome via the Back button (fallback parent path works); guard redirect from /plan lands on sign-in with one Back going to the previous screen; view transition runs with data-nav forward/back and the reduced-motion rules are served; 768 and 1280 show the Back button inside the centred frame with no overflow. Fix before done:
1. No scroll reset on navigation. useScreenTransition focuses with preventScroll and nothing scrolls to top. Verified: with two tall screens, scrolled to 900 on /welcome, a push to /why leaves scrollY at 900 (and Back returns to 900 only by accident). On a phone, tapping the bottom CTA of a long screen (Reveal, Sign-in details) lands the next screen mid-page. On a forward path change scroll window (phone) and the .app-scroll container (768+) to 0 inside the swap; leave Back to the browser or restore the same way. Add a test.
2. Sign-in has its own step (email > code) that is not in the URL. At the code step the header Back and the browser Back both leave sign-in to /reveal and lose the typed email; only the in-screen "Use a different email" link steps back. The card says step-back inside Discover "and other flows". Either put the step in the URL like Discover or make the shell Back defer to the screen's own step-back, and add a test.
3. Guard redirect flashes a blank screen. Verified by sampling: a signed-out push to /plan first animates to an empty Shell (resolve returns {to}, Shell renders null), then replace() runs a second transition to sign-in (a NONE frame between the two). Resolve the guard before starting the transition (or skip the transition when resolve gives {to}) so a redirect never animates through a blank.
Lower priority, fix in the same pass:

5. src/components/nav/nav.css line 5 `.screen:focus{outline:none}` is dead: base.css already removes the outline for [tabindex="-1"]. Delete. Shell hardcodes `path !== '/welcome'` for the root; a `root: true` on Route (or reading the flow's first entry) avoids a magic string.
6. oxlint warns react(set-state-in-effect) at useScreenTransition.ts:25. Not a blocker, but either derive the shown hash during render or add a one-line justification comment.
7. In dev (StrictMode) the first-mount guard `first.current` is defeated by the double effect run, so the first load focuses the h1 (seen at /welcome). Production is fine; use a ref that is reset in cleanup or compare against the previous path instead.
Files: edits outside the card's list (Discover.test.tsx, shell.test.tsx, useDiscover.ts, src/shell/*) are disclosed and justified; no other card's files appear touched. Components-importing-from-shell coupling (components/nav imports ../../shell/nav.ts) is acceptable for now.
