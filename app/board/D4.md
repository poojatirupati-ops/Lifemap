# Responsive layout and app frame
status: done
deps: D2
files: src/components/layout/*, src/styles/layout.css, index.html (viewport-fit=cover), scripts/overflow-check.js, README.md

## Goal
Phone first full-bleed with env(safe-area-inset-*) padding and dvh heights (no 100vh jump), tabs bar pinned bottom; from 768px up a centred phone-width app frame (prototype's .phone look: rounded, shadow, 390 wide, scrollable inside) and a calm backdrop; landscape phones handled like the prototype's media query; text and touch targets scale sensibly; no horizontal scroll at 320, 375, 768, 1280.

## Done when
screenshots at 320, 375, 768, 1280 of Welcome, Discover, Reveal and Sign-in show no overflow or clipping; a test or script checks document.scrollWidth <= innerWidth at those widths.

## Review (round 1, score 3)
Checked in the browser at 320, 375, 768, 1280, 844x390. Layout works: full-bleed phone, centred 390px frame with prototype shadow, inner scroll, tabbar/ask/toast pinned inside the frame at 768+, no overflow on Welcome, Discover, Reveal, Sign-in at 320 and 375 (no element past the viewport). vite build passes; npm test has 6 failures in other cards' files (shell, Discover, signIn tests; matchMedia), none in layout. Fix before done:
1. The overflow check cannot fail. `body` and `.app-scroll` both have overflow-x:hidden, so an overflowing child never reaches documentElement.scrollWidth (verified: a 3000px div inside .app-scroll gives .app-scroll scrollWidth 3000 but documentElement.scrollWidth stays 1280). scripts/overflow-check.js therefore passes whatever the content does. Measure what can fail (every element's getBoundingClientRect right <= innerWidth, or .app-scroll scrollWidth <= clientWidth), and consider dropping the blanket overflow-x:hidden so overflow bugs show up.
2. The script is also wrong at 768: the iframes keep the default 2px border, so the 768 case runs at 764px (full-bleed, frame never exercised) and 1280 at 1276. Set border:0. It is a paste-into-console snippet, not a test or runnable script; Done-when asks for a test or script that checks; make it run (vitest cannot do layout, so a node script using Playwright is out of scope; a console snippet is acceptable only if it can fail and uses border 0).
3. The bottom sheet pokes out of the frame's rounded corners at 768+. dialog.ui-sheet is in the top layer so the frame cannot clip it; it is 390px wide with square bottom corners sitting exactly on the frame's bottom edge, so white corners show over the dark ring (screenshot at 1280x800 with a sheet open). Give it bottom radius (48px) at 768+ or inset it, and check the Ask sheet.
4. Tab bar is not full width in full-bleed mode. shell.css `.tabbar{max-width:480px;margin:0 auto}` is not overridden, so on landscape phones (844x390: bar is 480 wide at x=182) and 480-767 wide screens the bar is a floating strip narrower than the page, while the Ask button sits at the real right edge. Add `.app-frame .tabbar{max-width:none}` (the frame already limits width at 768+). The prototype's landscape rule also compacts the tab bar (48px, icon and label in a row); at least confirm the bar and Ask do not cover content in landscape.
5. The card asks for screenshots at 320, 375, 768, 1280 of the four screens; the writer took two. Not verified by the writer: safe-area insets, landscape, sheet inside the frame (point 3 is what that would have found).
Minor, check while you are there: with View Transitions the `screen` snapshot slides 28px in the top layer, so on desktop it is not clipped by the frame's rounded overflow (add `::view-transition-group(screen){overflow:clip}` or similar and look at a mid-transition frame).

Remaining:
1. Safe-area insets are only half done. index.html has viewport-fit=cover, left/right/bottom are handled for the tab bar, but nothing pads the top for screens that have no .navbar: Welcome's .cover-logo is top:24px (welcome.css) so on a notched iPhone the logo sits under the status bar or island, and .cover has padding-bottom 32px with no env(safe-area-inset-bottom) so "I have an invite / Why we ask" sit on the home indicator. Card says full-bleed with env(safe-area-inset-*) padding; add the top and bottom insets in layout.css (e.g. `.app-frame .cover-logo{top:max(24px,env(safe-area-inset-top))}` and cover bottom padding with the inset; check Discover, Reveal and Sign-in CTAs at the bottom too). Round 1 listed safe-area as unverified and it still is.
2. The view-transition clip does not do what the comment says. I paused the `screen` transition mid-way at 768 (animation-play-state:paused on old/new) and the incoming snapshot shows square top-left and top-right corners over the dark ring and rounded frame: `::view-transition-group(screen){overflow:clip}` only clips to the group's own rectangle, and the pseudo-elements live in the top layer, so the frame's border-radius never applies. Fix by rounding the group at 768+ (e.g. `::view-transition-group(screen){border-radius:48px}` inside the same media query as the frame, or give the group a clip-path inset round 48px; check the result with the same paused-transition method) or by turning the slide off inside the frame. Writer said this was not inspected; it is visibly wrong.
3. Frame look vs prototype end-state .phone (line 431 of the prototype, computed: box-shadow 0 0 0 10px #0E0F12, 0 0 0 11px #2B2F33, 0 30px 70px rgba(14,26,35,.28); background #F2F5F6). App uses a #0B1F22 ring, no 11px hairline ring and .35 shadow. Small, but the card says the prototype's .phone look: port the computed values.
4. Housekeeping: the injected .tabbar the writer left in the dev tab was still in the DOM when I started (the earlier Welcome 375 screenshot showed it over the footer links); not a code defect, but remove injected markup before any screenshots. scripts/overflow-check.js is not on the card's file list (acceptable as the Done-when script; mention it in the card files line) and is not referenced from package.json or README, so nobody will find it: add one line in README or a `// ` pointer where the layout is documented.
