## Goal
GET and PUT /plan, session required, ONE JSON plan per user (scoped by session userId, never by a client id), version counter, stale write 409, zod validation against the Plan type imported from ../app/src/state/types.ts. Rejects nothing the customer typed; no PII beyond the plan and account is logged.

## Review (changes)
Build, lint and all 4 api tests pass. I also drove planRoutes with probes (temporary test, deleted). Verified good: 401 anonymous, round trip, 409 stale, 400 invalid, user B isolation (session userId only, body userId ignored), CAS is a single statement, unknown keys dropped, "__proto__" key harmless, only plan.ts, plan.test.ts and api/package.json (zod) touched. Issues:
1. PII in logs (violates the card's Goal "no PII beyond the plan and account is logged"). Any DB error is logged by Hono's default onError with Drizzle's message, which includes the full query params, i.e. the whole plan (name, email, mobile, dob). A client can trigger it: PUT {version:0, plan:{...whyNote:"a\u0000b"}} gives 500 and the console shows the entire plan JSON; the same for version 3000000000 (int4 overflow, 500). Fix: catch around the DB calls and return a generic 500 without logging params (or log only the error code), and make a test that triggers it and asserts no plan text reaches console.error.
2. Those two inputs should be 400, not 500: cap `version` (z.number().int().min(0).max(2147483646)) and reject U+0000 in strings (Postgres jsonb refuses it) or strip it before storing. Add both to the invalid-body test loop.
3. No body size limit: a 5MB plan is accepted and stored (5,000,000-char whyNote returns 200). Any logged-in user can store arbitrary volume. Add Hono bodyLimit (e.g. 1MB) on PUT /plan returning 413 and test it; this does not reject anything a customer types in practice.
4. Ownership gap: B3 says B11 must add the plan table to db/schema.ts and a migration, but B11's files are routes/index.ts, app.ts and coverage.test.ts, and no other card lists schema.ts. drizzle.config.ts reads only ./src/db/schema.ts, so the table would never be migrated and the route 500s in a real deployment while the test passes (it injects planRow via pushSchema). Fix on this card: add ../api/src/db/schema.ts to the files list and move planRow there (plan.ts imports it); or amend B11's card. Also the test then no longer needs `{...schema, planRow}` and the `as unknown as Db` casts.
5. Lower priority: the `satisfies z.ZodType<Plan>` drift guard only fails when Plan gains or narrows a field; removing or widening a Plan field leaves the schema compiling (output type stays assignable). Say so in the comment (or add a reverse assignment `const _: Plan extends z.infer<typeof planSchema> ...` check) rather than claiming it catches all drift. The claim "concurrent writes cannot both succeed" and "unknown keys are dropped" have no test; the second is a two-line addition.
